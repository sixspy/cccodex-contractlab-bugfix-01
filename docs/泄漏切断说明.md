# 泄漏切断说明（影子试跑通过数混入正式对账）

日期：2026-11-18 · 本仓链路（`05-contractlab`）· 库文件 `data/app.db` 照旧挂载

## 泄漏口径

`/api/reconcile`、`/api/ingress`、`/api/buffers`、`/api/policy`、`/api/review`
此前对 `ingress_batches` 全表计数，影子契约（`v4-shadow`，轨道=影子）的试跑
批次与正式批次同表存放，于是影子通过数被计入正式"通过"。`contracts` 表本身
已有 `track` 列，`ingress_batches` 缺轨道标记，是泄漏根因。

## 选定路径：乙路径（同表轨道标记 + 现场排除条件）

- 甲路径（影子批次只进影子表、对账永不读影子表）需要新表与新写路径；
  当日口径要求只动本仓链路、站点不新建，故不采用。
- 乙路径定稿：`ingress_batches` 增加 `track` 列（`正式` / `影子`）。
  正式对账**现场带 `WHERE track='正式'` 重算**，不物化任何正式快照，
  影子行永不进入正式计数。影子批次只写影子轨道，不写正式 `buffers`。

本说明当日定稿，不再改口。

## 边界

- 影子刷新（`POST /api/shadow/refresh`）只落影子轨道；正式入站校验
  （`POST /api/ingress/validate`）只落正式轨道。
- 历史泄漏回填 `repair_shadow_leak()` 只改写 `track` 一列；结果、说明、载荷、
  时间与**已拒收批次**一字不动。重复执行无副作用。
- 正式对账与影子刷新共用一把算账锁；同时抢算时后到者排队，并写一条
  `calculation_contention` 记录（对账响应 `contention` 字段可核）。
- 批次写入收敛到唯一入口 `insert_batch()`：写入轨道必须与契约轨道一致，
  否则拦成 409 并落一条 `leak_deviations`（泄漏偏了），业务写入整体回滚。
  `GET /api/leak/deviations` 可核偏离记录与争用记录。
- 展示层同步按轨道过滤，但隔离不依赖展示过滤：所有正式口径接口在 SQL 层
  已带排除条件，只改展示过滤不足以通过验收。
